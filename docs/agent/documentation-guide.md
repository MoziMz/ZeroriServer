# 문서 정리 가이드

## 목적

현재 구현과 일치하는 문서를 유지하되, 비밀값, 개인정보, 확인되지 않은 운영 정보를
복제하지 않는다.

## 정보의 우선순위

문서를 작성하거나 갱신할 때는 다음 순서로 내용을 검증한다.

1. 현재 구현과 테스트
2. `build.gradle`과 실행 설정 구조
3. 배포 워크플로와 운영 설정
4. 기존 README, API, 설계 문서

문서가 코드와 다르면 불일치를 적고, 확인된 코드 동작에 맞춰 문서를 갱신한다.
오래된 버전 정보는 근거 없이 유지하지 않는다.

## 문서 종류

| 종류 | 최소 내용 | 확인 대상 |
| --- | --- | --- |
| API 문서 | 목적, 메서드/경로, 인증 요구사항, 입력/출력, 오류 동작 | Controller, DTO, SecurityConfig, 예외 처리 |
| 설정 문서 | 필요한 변수명, 목적, 환경 범위, 비밀값이 아닌 예시 | `application*.yml`, config 클래스, 배포 워크플로 |
| 운영 런북 | 발생 조건, 근거 소스, 완화, 검증, 담당자 인계 | 로깅/모니터링 설정과 서비스 동작 |
| 아키텍처/컨텍스트 | 컴포넌트, 책임, 연동, 알려진 경계 | 패키지 구조, 빌드 설정, 외부 Client |

## 작성 규칙

- 확인된 현재 동작은 현재형으로 적고, 가정이나 계획 작업은 명확히 표시한다.
- 큰 코드 블록 복사보다 안정적인 개념과 근거 코드/설정 위치를 우선한다.
- 값은 `${VARIABLE_NAME}`, `[REDACTED]`, `example.invalid` 같은 자리표시자로 쓴다.
- 해석된 자격 증명, 비밀값이 포함된 URL, 사용자 기록, 원시 운영 로그를 문서화하지
  않는다.
- 중요한 동작은 그것을 정하는 코드나 설정 위치를 가리킨다.
- Controller, Service, Repository, 요청 DTO, 응답 DTO, 프로필 같은 코드베이스 용어를
  일관되게 사용한다.

## 갱신 절차

1. 변경된 동작 또는 오래된 설명을 찾는다.
2. 관련 Controller, Service, Repository, 설정과 테스트를 읽는다.
3. 해당 동작을 설명하는 가장 작은 문서 영역을 갱신한다.
4. 오래된 버전, 깨진 경로, 근거 없는 주장, 민감정보가 없는지 다시 읽는다.
5. 해결되지 않은 질문은 추측하지 말고 검증 항목으로 남긴다.

## 검토 체크리스트

- [ ] 기술 버전은 오래된 README가 아니라 `build.gradle` 기준이다.
- [ ] 인증과 인가 설명은 `SecurityConfig`, `Constant`과 일치한다.
- [ ] 업로드, 외부 Client, 관측성 설명이 현재 코드와 일치한다.
- [ ] 예시 요청과 로그는 합성 데이터이거나 마스킹되어 있다.
- [ ] 현재 동작과 미래 작업을 구분해 작성했다.
