# 코드 리뷰 가이드

## 입력과 프로젝트 규칙

먼저 Git diff를 읽고, 이후 동작 영향을 판단하는 데 필요한 연결 코드만 읽는다.
스타일이나 멤버 순서를 판단하기 전에는 `.github/CONVENTION/`의 원본 규약을 읽는다.

| 변경 영역 | 필수 컨벤션 |
| --- | --- |
| Controller | `controller.md` |
| Service | `service.md` |
| Repository | `repository.md` |
| Entity | `entity.md` |
| 응답 DTO | `res.md` |

프로젝트 규약과 충돌하지 않고 실제 유지보수성이나 동작 문제도 없다면, 개인적인
스타일 선호를 결함으로 보고하지 않는다.

## 리뷰 절차

1. diff와 영향 API 또는 유스케이스를 바탕으로 의도된 동작을 요약한다.
2. 변경된 데이터가 Controller, Service, Repository, 외부 Client, 응답으로 흐르는
   경로를 필요한 범위에서 추적한다.
3. 오류 처리, 인가, 검증, 영속성, 외부 부작용을 확인한다.
4. 테스트를 확인하거나 변경 동작을 보호할 누락 테스트를 식별한다.
5. 공통 운영 규칙의 형식으로 파일/라인 근거가 있는 실행 가능한 발견 사항만 보고한다.

## 점검 항목

| 영역 | 확인 내용 |
| --- | --- |
| Controller | 요청 바인딩/검증이 명확한지, 응답과 상태 코드가 API 계약에 맞는지, 비즈니스 로직이 과도하게 섞이지 않았는지 |
| Service | 비즈니스 규칙의 소유 위치가 적절한지, 트랜잭션 경계가 읽기/쓰기에 맞는지, 오류 경로가 기존 애플리케이션 예외를 유지하는지 |
| Repository/JPA | 쿼리가 유스케이스와 맞는지, 불필요한 N+1 가능성이 없는지, 페이지/필터가 정확한지 |
| 외부 호출 | 타임아웃, 오류 매핑, 부작용을 고려했는지, 비밀값이나 원격 응답을 노출하지 않는지 |
| 보안 | 엔드포인트 인가가 `SecurityConfig`, `Constant`과 맞는지, 사용자 제공 식별자에 소유권 검사가 있는지 |
| 데이터와 null | 선택값, 빈 컬렉션, enum, 영속성 불변 조건이 안전한지 |
| 관측성 | 민감한 요청 본문을 남기지 않으면서 의미 있는 실패 추적이 가능한지 |

## 심각도

심각도 정의는 `agent-operating-rules.md`를 따른다. 예시는 다음과 같다.

- `critical`: 강한 근거가 있는 인가 우회, 자격 증명 노출, 파괴적 데이터 훼손
- `high`: 소유권 검사 누락, 데이터 유실 가능 트랜잭션 오류, 일반 경로의 운영 API 실패
- `medium`: N+1 회귀 가능성, 예상 가능한 오류 미처리, 데이터 불일치를 만드는 검증 누락
- `low`: 영향이 작은 컨벤션 위반 또는 하드닝 항목
- `info`: 담당자 확인이 필요한 관찰 또는 테스트 제안

## 출력 요구사항

모든 발견 사항에는 대상 파일과 라인, 간결한 사실, 영향, 구체적인 권장 조치를
포함한다. 실행 가능한 문제가 없으면 그 사실을 명시하고, 테스트되지 않은 오류 경로
같은 잔여 위험을 적는다.

## 검증 예시

`MultipartFile`을 받는 Controller 변경을 리뷰할 때는 연결 Service,
`S3ImageService`, 엔드포인트 인가, 파일 타입과 크기 검증, 실패 동작을 함께
검토한다. 업로드 기능이 존재한다는 이유만으로 취약점이라고 보고하지 않고, 확인한
코드 동작에 근거해 판단한다.
